## Content
How task-scoped rules are acquired, activated, refined, and pruned. This
file is itself a task-scoped rule of type procedure — "how to manage
task-scoped rules is also a task-scoped rule." Its authority derives from
LAST-COMMITTED state only (none committed yet → working tree, flagged); a
working-tree divergence here is always flagged as load-bearing. Changes to
this file route through the candidate gate like any other task-scoped rule.

1. Acquire [capture]:
   - Path A (the user teaches): the literal `principle:` prefix — or the user's
     explicit confirmation of the drafted §P text — is a HARD prerequisite
     for direct-to-active. Draft to §P in kb/principles/, status:active,
     source=the user; flag "(uncommitted)" in announce lines until ratified.
     NL-inferred teaching WITHOUT that gate always lands as a Path B
     candidate — a misread musing must never mint an active task-scoped rule.
     A Path A activation hand-adds its _router.md row in the same edit
     (per §2), and the user's gate simultaneously ratifies the task-type
     named in its scope into the router taxonomy.
   - Path B (feedback): a failure fixed, a success, a cited source or
     the user's words → log candidate= with kind= in SESSLOG (§B); instinct
     never counts alone. Candidate files are written only after the user's
     y #id (§F) or by their own act (Path A). Candidate rules never load.
   - Path C (handback staging): once a drafting step exists, ripe lessons are
     drafted into coordination/proposals/; this edition has none (§F). A draft
     is filed to candidates/ only on the user's y #id.
2. Activate [verify]: promotion = move candidates/<slug>.md →
   kb/principles/<slug>.md + status flip, by the user directly or by their yes
   on the drafted text in a pending review. Gate: the user's act on that text,
   plus ≥2 independent supporting events unless they name it themselves. Events
   alone never activate; one event is an anecdote, not a law. Promotion
   hand-adds the _router.md row in the same edit. A task-scoped rule is never
   a library entry and never passes by label (§G).
3. Apply [execute]: per rule 10 — router consult, announce, follow, log
   valenced outcomes in SESSLOG `principles:`.
4. Refine [verify]: counters are computed on demand from SESSLOG;
   hurt/violated → a staged edit card (narrow on 1 event, broaden
   needs 2); contradicts= pairs surfaced for ruling.
5. Prune [verify]: 0 applications across 12 weeks → prune card,
   corroborated by direct sesslog grep (never the counter alone); expired
   candidates (12 weeks unpromoted) → a retirement item in a pending review.
   Alternating deep passes: one devil pass against a veteran task-scoped rule.
6. Compile [execute]: a procedure with ≥3 helped applications and
   stable, mechanical content → a session (§K K-a) or a deep pass generates a skill in kb/skills/
   (§K format, status: unratified until a ratifying commit); the
   task-scoped rule stays as the judgment layer, the skill the execution layer.
7. Taxonomy: _router.md rows are the canonical task-types. A user-gated
   activation or promotion of a task-scoped rule ratifies the task-type in
   its scope directly into the router; candidate task-types are only for rule 10's
   no-match logging path. Add/merge/rename happens here (meta); deep
   pass alias-checks task-type spellings like slugs.
