## Content
How principles are acquired, activated, refined, and pruned. This file is
itself a procedure principle — "how to manage principles is also a
principle." Its authority derives from LAST-COMMITTED state only (none
committed yet → working tree, flagged); a working-tree divergence here is
always flagged as load-bearing. Changes to this file route through the
candidate gate like any other principle.

1. Acquire [capture]:
   - Path A (the user teaches): the literal `principle:` prefix — or the user's
     explicit confirmation of the drafted §P text — is a HARD prerequisite
     for direct-to-active. Draft to §P in kb/principles/, status:active,
     source=the user; flag "(uncommitted)" in announce lines until ratified.
     NL-inferred teaching WITHOUT that gate always lands as a Path B
     candidate — a misread musing must never mint an active principle.
     A Path A activation hand-adds its _router.md row in the same edit
     (per §2), and the user's gate simultaneously ratifies the task-type
     named in its scope into the router taxonomy.
   - Path B (feedback): notable failure/success/correction → log a
     `candidate:` one-liner in SESSLOG; if it deserves more, draft a full
     file in kb/principles/candidates/. Candidates never load.
   - Path C (ritual mining): repeated friction across episodes → ritual
     drafts candidates.
2. Activate [verify]: promotion = move candidates/<slug>.md →
   kb/principles/<slug>.md + status flip, by the user directly or by the user
   ratifying a ritual proposal. Gate: the user's say-so, or ≥2 independent
   supporting events. One event is an anecdote, not a law. Until ritual
   regeneration exists, promotion includes hand-adding the _router.md row
   in the same edit.
3. Apply [execute]: per rule 10 — router consult, announce, follow, log
   valenced outcomes in SESSLOG `principles:`.
4. Refine [verify]: ritual reconciles outcomes into counters (sole writer);
   hurt/violated → proposed edit in the Brief (narrow on 1 event, broaden
   needs 2); contradicts= pairs surfaced for ruling.
5. Prune [verify]: 0 applications across ~4 rituals → prune proposal,
   corroborated by direct sesslog grep (never the counter alone); expired
   candidates (≥4 rituals unpromoted) → dead pile, noted in Brief.
   Alternating rituals: one devil pass against a veteran principle.
6. Compile [execute] (future): a procedure with ≥3 helped applications and
   stable, mechanical content → ritual proposes compiling into a skill
   (a skills layer, when built); the principle stays as the judgment
   layer, the skill becomes the execution layer.
7. Taxonomy: _router.md rows are the canonical task-types. A user-gated
   principle activation or promotion ratifies the task-type in its scope
   directly into the router; candidate task-types are only for rule 10's
   no-match logging path. Add/merge/rename happens here (meta); ritual
   alias-checks task-type spellings like slugs.
